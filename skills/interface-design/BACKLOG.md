# interface-design 待办

`design-check.cjs` 当前覆盖不到、值得后续投入的方向。每条写明触发条件——满足了才动手，不满足就不值这个成本。

## 1 · 用显著性模型替换灰度模糊算焦点

**现状**：`design-check.cjs` 用灰度 + 高斯模糊 + 网格连通区域近似眯眼测试。它对「大色块抢焦点」这类问题判得准，对「元素多、明暗接近、靠形状与语义区分主次」的密集版面判得粗。

**升级路径两条**：

- **OpenCV `StaticSaliencySpectralResidual`** — 解析算法，无需下载模型，`uv add opencv-contrib-python` 即可。对图像做对数频谱残差变换得到显著图，模拟前注意视觉搜索。成本最低，抽象出的元素边界比灰度模糊干净。
- **MIT UMSI（Unified Model of Saliency and Importance）** — 深度模型，专门在 posters、infographics、mobile UI 上训练，配套 Imp1k 数据集（1000 张设计稿的众包重要性标注）。它预测的是「设计稿里哪块**重要**」，不只是「哪块**跳**」，这是它和纯显著性模型的分界。模型与论文在 https://predimportance.mit.edu/ ，论文 arXiv:2008.02912（UIST 2020）。

**什么时候走这条路**：现有脚本在真实设计稿上出现「算出的第一焦点与人眼所见明显不符」的案例，且累计到三例以上、能归纳出共同特征时。单个反例先当作阈值调优处理。

## 2 · 判断文字该不该占这块地方

**现实痛点**：agent 出设计稿最常见的毛病不是焦点错，是**往页面上堆大量不承载信息的文字**。

**现状**：`design-check.cjs` 输出版面密度指标——墨水占比、每屏字符总量、文本块数、平均块长度、最长块长度。它量得出「这屏塞得过满」，量不出「这段话本身没有内容」。

**两条互补路径**：

- **语义侧**：文本块逐块过 `de-ai-writing` 的所指测试——把句子里的具体所指抽掉后还剩不剩内容。这条不需要视觉模型，可以现在就做，代价是每块文字一次判断。
- **视觉侧**：UMSI 预测每个文本块的重要性得分，得分低而占地大的块就是候选删除项。它的训练数据里 infographics 与 poster 占比高，正好是文字密集的版式。

**什么时候走这条路**：密度指标报出「过满」但 agent 依据它删不动的情况反复出现时——说明缺的不是「多了」这个判断，是「删哪块」这个判断。

## 3 · 覆盖 HTML 之外的载体

**现状**：脚本只吃 HTML。小程序 wxml、PPT、图片稿走不了。

**路径**：这三类的共同点是能拿到一张真实截图。把脚本的图像分析部分（灰度模糊、网格、连通区域、密度指标）拆成独立入口，接受 PNG 输入，跳过 DOM 映射，输出坐标区域而非元素选择器。DOM 映射是 HTML 独有的红利，其余分析对任何截图都成立。

**什么时候走这条路**：小程序页面、PPT、图片稿的视觉评审开始高频出现时。

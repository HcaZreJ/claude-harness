# 界面设计纪律（信息层级优先）

默认生成的界面有一套已被看厌的样式：渐变英雄区、每条列表配一个 emoji、万物皆圆角卡片、三种颜色各自高亮。它们的共同病根只有一个：**装饰不编码信息**。守住下面这条总纲，那套样式自然不会出现。

## 0 · 总纲：每个视觉差异必须编码一个信息差异

颜色、字号、字重、背景、边框、图标、emoji、阴影、动效——任何视觉差异，说不出「它对应什么信息差异」，就是设计熵：消耗读者注意力，不传递任何东西，积累三四处读者就不知道自己在看什么了。反方向同样成立：**同一含义永远用同一样式，同一样式永远只表示同一含义**（跨屏、跨页一致）。

原因：读者默认「样子变了 = 意思变了」，看到不带含义的变化会先去猜它编码了什么，这趟注意力白付；反过来，读者必须拿到的每条信息，都要有一处可感变化与它对应，否则读者不会注意到。差异要大到一眼分得出：字号差两三个像素、灰度差一档、间距差得不明显，读者分不出来，这处差异就等于没做，还白占一层结构。检验：把画面缩小或眯起眼看，差异还在不在。

（理论根源：Tufte 的 data-ink / smallest effective difference——一切视觉区分做到刚好有效为止；NN/G 一致性启发式。）

**工作流三步，顺序执行：**
1. **先写信息层级大纲**（纯文字，动样式之前）：这一屏的唯一目标是什么 → 用户第一眼该看什么 → 次级信息有哪几组 → 哪些是元信息（来源/标签/时间戳）。
2. **再上样式**：§1 十条硬规则，每个样式差异对应大纲里的一个层级差异。
3. **做完跑 §3 的脚本**，据它的输出按 §2 逐条自检并修。结构先于皮肤——层级大纲错了，再精致的样式都是熵。

## 1 · 十条硬规则

1. **一屏一焦点**。每屏有且只有一个最先抓住眼睛的元素，且它必须正好是这屏最想让用户看的东西。两个高亮元素同屏就是打架（包括一个亮按钮 + 一个置灰按钮：置灰的仍占注意力）。原因：面积、明暗对比、饱和度、被留白包围的程度，谁的差异最大谁拿走第一眼，其余每一处强对比都在和焦点抢。检验：给每屏根元素写上 `data-focus`，跑 §3 的脚本核对实际焦点是不是它。

2. **强调色单义，红色专属警示**。强调色在整个产品里只有一个含义（通常 = 主动作/当前位置）；一屏只出现一处。红色只出现在错误、危险、删除、警告——用红色「划重点」是给读者报假警：读者带着警惕先读它，读完发现是普通信息，白付一次注意力。颜色之外必须有图标或文字兜底（色弱可感知）。

3. **并列即同级**。同款元素排在一起 = 向读者声明「这些是同一母类下的平行成员，可任意顺序读」。检验每个并列组：找出共同的「总体」名词（步骤？选项？时间点？角色？）——找不到的成员拆出去；组内有先后/因果/从属关系的，改用序号、时间轴、嵌套结构，让顺序由结构承载而非靠读者猜。

4. **同级同装**。同一并列组内，标题有无、字号、字色、图标、背景完全一致。想让某一项特殊，先说出它编码了什么信息差异，且优先用位置或序号表达差异，其次才是颜色/背景。

5. **字阶 ≤3，灰字只放元信息**。一屏字号种类 ≤3（标题/正文/辅注）。灰色小字 = 「可跳过」层，只放来源、时间戳、标签；把正文内容写成灰色 = 亲手把内容降级。

6. **并列数 ≤4**。工作记忆的现实容量约 4 个组块（Cowan 对 Miller 7±2 的修正）。同级并列元素超过 4 个，先合并成更高层组块，再考虑分屏/分页。凡是要读者自己心算、跨屏对照、记着上一屏数字才读得懂的地方，界面替他算好，把要比的东西摆到一起。

7. **分组靠间距，结论放前面**。组内间距明显小于组间间距（至少 1.5 倍）——间距本身就是「这是一伙的」的语言；留白是层级工具，不是剩余空间。原因：读者不需要提示就把距离近、外观一致、对齐在同一条线上的元素当成一伙，并按组理解和记忆；你没主动划的组，读者会自己划一个，通常和你想的不一样。屏内自上而下线性扫视：结论性信息放屏顶，关键词放标题开头。

8. **组件隐喻贴合**。现成组件自带隐喻：进度条 = 进度，打字光标 = 正在生成，漏斗 = 逐层流失，勾选 = 完成。借用组件时旧隐喻会跟着过来——数据语义与组件隐喻不合时（比如拿「正在生成」的打字动画去展示统计占比），读者先按旧隐喻理解、再花力气纠错，比不配图更糟。换皮肤，别硬套。自己画的形式同理：时间从左往右、数值越大画得越长、有先后用序号、有从属用缩进；形式与含义拧着时，读者先按形式理解一遍再纠正，比不给形式更慢。

9. **信息角色三分**。一屏上每块信息必须可见地属于三种角色之一：**读者自己的数据**、**教他怎么读的说明**（图例、规则、定义），或 **让他做的事**（按钮、可复制指令）。三种角色各穿各的衣服：说明类永远比数据小一号、灰色、装进独立容器（带框，或带「怎么读」类小标题），绝不和数据行共用同一种行样式——和数据同装的解释文字，读者要么当成数据、要么整个略过（CFPB 房贷披露表十轮真人测试：无容器的解释标签被全体受试者跳过，换独立灰框加粗后才被注意到）。图例贴着它解释的那块数据，能把标注直接写在数据上就不单设图例。术语、缩写、图标、颜色约定，读者手里没有的那一份当场给出，或换成读者已有的说法；松紧看读者：给熟手用的内部工具可以直接上行话，面向新用户的页面每个专有名词第一次出现就自带解释。

10. **折叠与强调有判据**。只有「一部分读者才需要」的信息允许收进点开再看；多数读者需要的信息不得折叠（GOV.UK details 组件判据）——给它一句版面上直接可见的话，长解释才进折叠，折叠入口的文字写清展开后能看到什么。强调块（高亮、警示、inset）每屏不超过 2 个，两块之间至少隔一段正文（NHS 配额）；复杂版面上的浅底强调块容易被看漏，最重要的信息不交给它承载。

## 2 · 单屏自检（完成后按序执行）

先跑 §3 的脚本拿事实，再逐条给结论。第 1 条由脚本判定，不匹配就改到匹配；其余脚本只供事实，结论由你写。某条规则为了传达特定含义被刻意违反时（例如刻意堆满来传达「混乱」），写出这处违反传达了什么平铺直叙传达不了的信息。

| # | 自检 | 脚本给出 | 你给出 |
|---|---|---|---|
| 1 | 唯一焦点存在，且正是本屏最重要的东西 | 吸引力排序、期望与实际是否匹配 | 不匹配时改到匹配 |
| 2 | 一句话概括本屏唯一目标 | — | 概括时需要「和」连接两件事就拆屏 |
| 3 | 并列组说出共同总体名词，计数 ≤4，组内同装 | 成员数、组内间距、组内不一致的样式属性 | 共同总体名词；说不出的成员拆出去 |
| 4 | 逐个视觉差异说出编码的信息差异 | 全部颜色、字号、强调色的使用点 | 每处差异编码了哪个信息差异，说不出的删 |
| 5 | 红色只出现在错误、警示语义 | 全部红色系使用点 | 每处的语义是否成立 |
| 6 | 字阶 ≤3，灰字只放元信息 | 字阶种类与用例、被调淡的文本 | 每处灰字是不是元信息 |
| 7 | 跨屏样式含义零冲突 | 按屏分段输出便于对照 | 同一样式在各屏是不是同一含义 |
| 8 | 版面没有堆不承载信息的文字 | 墨水占比、字符总量、文本块数、最长块 | 哪一块删得掉 |
| 9 | 每块信息的角色（数据/说明/动作）一眼可辨，说明类独立容器且降一档 | 灰字、边框、深底浅字清单 | 逐块归角色；说明块与数据行是否同款式 |
| 10 | 折叠的都是「部分人才需要」；强调块 ≤2 且间隔正文 | — | 逐个折叠块、强调块给判断 |

第 8 条是出稿最常翻车的地方：文字堆到满屏，每句单独看都通顺，合起来没有一处是这屏唯一目标必需的。逐块问：删掉它，读者还能完成这屏的目标吗——能删就删；目标必需的信息缺一条，读者就卡住去别处找，删不掉的检查它是不是摆在读者会读到的位置。脚本量得出「塞得过满」，量不出「这段本身没内容」——后者把文本块逐块过 `de-ai-writing` 的所指测试。

## 3 · 跑检查脚本

```
node ~/.agents/skills/interface-design/scripts/design-check.cjs <html 路径> [--viewport 1440x900] [--shots <目录>]
```

动样式之前，先给每屏根元素写上期望焦点：

```html
<section class="screen" data-focus=".cta">
```

意思是「这屏我要读者第一眼看到 `.cta`」。脚本真截图、对截图做灰度加高斯模糊（眯眼的物理本质就是低通滤波）、算出画面上最抢注意力的区域、按几何映射回 DOM 元素，逐屏核对实际焦点是不是你声明的那个。

输出三段：

- **焦点核对** — 本屏吸引力排序（谁抢走百分之多少）、期望与实际是否匹配。不匹配以退出码 1 结束。第一名领先第二名不足 1.5 倍时报焦点竞争。
- **版面密度** — 墨水占比、字符总量、文本块数、平均与最长块长度。阈值按中文正文标定，英文稿的字符类阈值按 1.6 倍放宽再读；读者习惯高密度版面时阈值放宽，前提是焦点与分组仍然一眼成立。
- **事实清单** — 字阶、灰字、深底浅字、红色、强调色、并列组、同级同装。

脚本在设计稿同目录落两张 PNG：原样一张，眯眼一张。眯眼图是判定的原始依据，读它能核对排序，也能看出脚本量不到的东西——组件隐喻是否贴合、整屏节奏是否顺。对着眯眼图再答两问：只看轮廓能不能把三种信息角色（数据/说明/动作）分出来；长得一样的几块是不是真属同一角色——答不出任何一问就回规则 9 改容器与档位。

依赖 node 与 playwright。缺了它会打印安装命令并以退出码 3 结束，这时在报告里写明本次未跑视觉检查及原因。

脚本吃 HTML。小程序 wxml、PPT、图片稿改用真机或渲染后的截图，由人核对焦点。

后续升级路径（换更强的显著性模型、判断文字该不该占地方、覆盖 HTML 之外的载体）与各自的触发条件记在 `BACKLOG.md`。

## 4 · ✗→✓ 微案例

✗ 四张同款卡片竖排：「他们的开局」「30 天后」（红底高亮）「问题在哪」（红点 bullet、灰色正文）「是不是很眼熟？…」（无标题、大字金句）。问题：并列组找不到共同总体（前两张是时间叙事、第三张是分析、第四张是抒情）；红底无警示语义却抢走第一眼；四张卡标题有无、字号、颜色、bullet 全不一致。

✓ 前两张合并为一条两节点时间轴（顺序由结构承载，同装、无高亮）；分析降为一句正文；抒情卡删除；第一眼焦点回到标题与主按钮。

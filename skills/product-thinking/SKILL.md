# 产品思维

产品思维回答「谁的什么困境值得解决、怎样解决才会有人付钱」；技术思维回答「怎么造出来」。两者的根本差别在裁决者：技术判断的对错由系统运行结果裁决，产品判断的对错由别人的真实行为裁决——用不用、付不付钱、留不留下。因此产品思维的全部纪律归结为一件事：**用外部证据代替自我投射**。

产品立得住 = 一条证据链完整：**具体的人 × 具体的挣扎时刻（他此刻真实卡住的地方）× 胜过现状的价值 × 付出代价的证据 × 成立的交易（有人愿意付钱，且这笔买卖双方都算得过账）**。链的强度由最弱一环决定，评审的产出是指认最弱一环，不是逐环打分求平均。链上任何一环用愿景、技术能力或自我投射充数，产品就还是 demo。

## 第零步：把问题和方案拆开

- 「问题是我们缺少 X 功能」是把方案伪装成问题（下称方案走私），问题本身从未被验证。先重写成：谁，在什么场景，卡在什么地方，现在怎么凑合，代价是什么。
- 用户的原话是方案候选，不是需求。三层校验（苏杰 Y 模型）：用户原话（往往是他自己想的方案）→ 用户目标（追问为什么得到）→ 产品功能（重新设计的方案）；三层之间要能相互推导，推导不通说明中间有臆断。用心听，但不要照着做。
- 落笔前把思考路径反转一次：从「我/团队 → 想做的功能 → 用户」改写成「用户 → 需求 → 功能」，再读一遍还成不成立。

## 价值链五环

评审任何提案，逐环找证据；每环写下「证据」或「缺口」。

### 环 1 · 谁，在哪个挣扎时刻

- 用户不是自然人，是需求的集合（俞军）：同一个人在不同场景是不同用户，调研样本按场景切分，不按人群切分。
- 指认一个具体的挣扎时刻（struggling moment）：某人在某天因为什么具体卡住。指认不出来，需求大概率不成立——需求由挣扎时刻创造，不由产品创造。
- 痛点的门槛是恐惧——错过、失去、丢脸（梁宁）。纯粹的不方便是痒点，是体验优化项，撑不起一个产品。
- 自检：目标用户的描述能让你想起一个具体的人吗？「忙碌的职场人」「想提升自己的年轻人」= 还没找到用户。

### 环 2 · 现状：没有我们，用户拿什么顶替

- 真正的替代品经常不是同类产品，而是「不做」「找人代劳」「Excel 糊弄」（April Dunford）。这一问不填实，后面所有差异化都是空中楼阁。
- 土办法是金矿：用户自己拼凑的笨拙替代方案（Excel 管客户、微信传文件、手抄清单）是需求真实存在且未被满足的最强行为证据；找不到任何土办法，警惕伪需求。
- 竞品按替代品关系选，不按行业标签选：同一批用户 × 同一个任务 × 同一种现状顶替方式。3 个真正近的竞品胜过 20 个同行业但不相干的——竞品调研的用处是回答「用户现在拿什么顶替、为什么还没被满足」，不是撑报告页数。
- 替代品清单里必须包含「用户已在用的平台顺手加一个功能」：平台搭售是最强替代品。追问「这东西会不会被 Jira/Notion/微信们一个 feature 做掉」，以及这个品类里前人（独立做同一件事的产品）活下来了吗、靠什么活的。

### 环 3 · 价值不等式：新价值翻得过替换成本吗

- 用户价值 = 新体验 − 旧体验 − 替换成本（俞军）。三项拆开单独评估：新体验不够强、旧体验本就不差、替换成本过高，任何一条都能让总价值归零。2018 年的聊天应用子弹短信，语音转文字体验确实胜过微信、上线即爆红，但用户的联系人和群聊全在微信，替换成本一项直接吃掉全部体验优势，数月内归零。
- 切换发生的条件：push（现状之痛）+ pull（新方案吸引力）> anxiety（怕出错）+ habit（惯性）（Bob Moesta 四力）。方案只堆 pull、不单独审计 anxiety 和 habit，是最常见的漏项——产品好不构成用户会换的证据。
- 深井胜过浅坑：少数人极度想要，胜过多数人觉得还行（Paul Graham）。验证要找「拿走会抓狂」的深度反应，不找「更多人说还不错」的广度。

### 环 4 · 证据分级：什么算数

证据从强到弱：

1. 已付出代价的行为：付费、预付、连续使用、押上声誉做引荐
2. 过去的具体行为：「上次遇到是什么时候？当时怎么处理的？」
3. 土办法的存在
4. 有代价的下一步承诺（Mom Test 的 commitment & advancement）

以下不算证据，出现即打折：

- 夸奖（「这想法太棒了」——零信息）
- 未来意愿（「我会用的」「我肯定买」）
- 功能建议（伪装成需求的方案——反问一层，挖它想解决的真实问题）
- 免费场景的使用数据（没有代价就没有 commitment）
- 自己或团队的强烈直觉（自我投射；直觉负责提出假设，数据负责证伪，不反过来）

访谈三规则（Mom Test）：谈他们的生活，不谈你的想法；问过去的具体行为，不问未来意愿；自己说话不超过三分之一。
分群再听（Superhuman PMF 引擎）：只深听高期望用户，主动放弃「无所谓」用户的意见权重——全量平均会把强信号稀释成「大家都还好」的假象。Superhuman 只是把本就不在目标市场的用户从分母剔除（留着他们是度量错误），PMF 分数就从 22% 跳到 32%。

### 环 5 · 交易成立：谁付钱、为什么、信任从哪来

- 先诊断 B 还是 C：这个方案回答的是「用户会不会爱上它」（C）还是「能不能证明 ROI」（B）？B 端决策者≠使用者，买的是 ROI、风险下降、合规，且需要一套可复述的购买理由带回组织内部；C 端购买者=使用者，情绪先行、事后理性化。把 B 端生意当 C 端做（或反之）的方案，整体重来。
- 付费意愿在造之前验证：钉住具体价格问「¥X/年你会续费吗」，不问「你愿意付多少钱」（Monetizing Innovation）。
- 功能三分类：Leader（客户为它付钱，产品围绕它设计）/ Filler（锦上添花，单独不构成购买理由）/ Killer（捆绑收费会吓跑交易）。核心价值免费送掉是 hidden gem 定价失误，不是获客慷慨。
- 信任是付费的前置条件，来源四种：权威背书、方法透明、社会证明、结果可解释。产品越是「用户无法自行验证质量」（测评、咨询、教育、医疗），信任建设越是与功能开发同级的工作。且「用户觉得准」和「真的准」可以完全脱钩——放之四海皆准的描述会被人当作精准命中自己（Barnum 效应），泛泛而谈能让人觉得准，却让不了它真的准。
- **内容质量本身是核心价值时，追问：质量上限由谁保证？** 工具放大产能，放大不了判断——判断要么来自有判断力的人（专家、名师、有实战履历的作者），要么来自可验证的方法论。给不出这个答案的内容型产品，用户不会为它付出超过尝鲜级别的钱。

## 打磨：从站得住到好用

价值链回答「该不该存在」；打磨回答「存在之后，怎么从能用变成好用」。打磨的对象不是界面，是关键用户行为的效率与确定性。

- 排查顺序：有趣 > 功能 > 交互 > UI（张小龙）——前一项不成立不看后一项；打磨 UI 之前先确认这个功能该存在。
- 把关键行为的完成成本降到最低：做产品的本质是提高用户的效率，且最高效不等于步骤最少——该由用户做的判断不能替他省掉。
- 确定性产生依赖（梁宁）：每次使用都能预期到会发生什么；频繁改版是在主动拆除依赖。
- 力气分两半（Superhuman）：一半加强高期望用户已经爱的主特性，一半逐个消灭核心任务上的中断点；为「无所谓」的用户改方向不属于打磨。
- 惊喜会贬值：今天的加分项会退化成明天的理所当然（Kano 的 delighter 退化），打磨是持续动作，不是一次性里程碑。
- 打磨到位的信号：新用户无需培训能上手；核心任务从头走到尾没有断点；用户开始自发向别人展示——传播的燃料是可展示的优越感，不是功能本身。
- 用户视角不靠自查：面向用户的页面与文案在交付前派冷读者 agent（`~/.claude/agents/cold-reader.md`）过闸——零背景实例逐段复述、列生词、答任务题，三实例两票判缺陷。写的人读自己的稿永远读得懂，所以「读不读得懂」只能由没有你上下文的读者来测。

## 三个高频工作流

### A · 评审提案 / 判需求真伪

1. 第零步：方案走私检查，重写出干净的问题陈述。
2. 五问定盘：谁需要？他在什么场景遇到了问题？现在怎么解决？现有方式的成本是多少？新方案真的比原来更好吗？
3. 逐环过价值链，每环写「证据 or 缺口」。
4. 结论 = 指认最弱一环 + 它需要的最小验证动作。输出围绕最弱一环组织，不平铺五环。

### B · 立项 / 写 PRD

1. 先写半页未来发布稿：产品上线那天，向目标用户宣布什么？自己念完不心动，方案毙掉或重写（Amazon working backwards）。
2. 失败前置（pre-mortem）：假设项目已经失败，列出三个最可能的原因；用三栏分开——真老虎（真风险）、纸老虎（别人担心但你判断不构成威胁）、大象（显而易见却没人说出口的问题）。
3. 每个信息缺口显式标注：🔶 假设（合理但未验证）/ 🔵 开放问题（需要调研）——不用编造的细节填缝。需要澄清时最多问 3 个问题，其余标注后继续。
4. 范围先定胃口（appetite）：先拍板这件事值得花多少时间和人，让方案适配数字；不是先设计再倒推工时（Shape Up）。
5. 路线图写业务成果（outcome）和待验证假设，不写功能名加日期——考核「造了多少」而不是「解决了什么」，是 build trap 的入口。

### C · 已有产品找「只改一处」

1. 七问扫描：产品服务谁？用户在什么场景下使用？用户原本有什么困难？产品帮用户完成的核心任务是什么？哪一步最容易中断？产品如何获得收入或持续运营？如果只能改一个地方，改什么？
2. 找关键用户行为：哪一个行为是其他一切行为、增长与商业化的共同基础？（菜谱社区下厨房的关键行为是用户上传菜谱：没有它，收藏、关注、一键下单全部失去地基。）「如何让更多用户完成关键行为」是最重要的一问。
3. 需求排序用两个轴：对用户的重要度 × 现有方案满足度，机会在「重要且不满足」象限。「提得最多」不等于「满足度最低」——声音大的需求可能已被竞品做得不错。
4. 改动方向对照上一节「打磨」逐条检查，动手前查确定性：会不会打破用户对产品行为的预期一致性？

## 反模式速查（症状 → 后果 → 纠正）

| 症状 | 后果 | 纠正 |
|---|---|---|
| 团队很忙、功能发得很快、业务指标不动 | build trap：把产出当成果，忙与有效脱钩 | 把「这周交付了什么」换成「这周学到了用户/业务的什么」 |
| 拿着技术能力找应用场景 | 锤子找钉子，需求是倒推编造的 | 从挣扎时刻正推；落地验收标准 = 一线用户无需培训能上手 |
| demo 给没用过的人看，反响热烈 | demo 的功能是制造信念，不是解决问题；观众会当场要 demo 撑不住的功能 | 产品的判据 = 有人反复用 + 付出代价 + 质量能持续交付 |
| 目标用户 =「所有想提升 X 的人」 | 没有具体的人 = 没有需求 | 按场景切出一类人，窄到能想起具体面孔 |
| 判断或解读换个产品名仍然成立 | Barnum 空话：感觉有理，实际零信息 | 删掉重写，钉在具体的人、场景、数字上 |
| 小规模验证顺利就外推 | 原型测试验证不了规模化后模型是否成立（产品人纯银对其失败产品「一罐」的复盘） | 单独追问：放大十倍后哪个环节最先崩 |
| 砍功能归因为「克制」「极简」 | 价值观姿态替代尽职调查 | 每个砍掉的功能给一条具体的「为什么行不通」（张小龙：是合理性，不是克制） |
| 为新点子找支持证据 | 验证自己的想法 ≠ 检验假设 | 默认否定姿态：新点子 99% 的情况下否定是对的，反驳不倒再推进 |
| 只评「技术上能不能做」 | 四大风险漏了三个 | 逐项过四关：价值（会不会有人买）、易用（会不会用）、可行（能不能做）、业务成立（卖得动、算得过账、合规），各有人签字（Cagan） |
| 评价所有产品都用「好不好用」 | 维度错配 | 先问「这个产品靠什么赢」再选评价维度：靠体验看细节、靠技术看准确度、靠运营看响应效率、靠独占资源看壁垒 |

## 输出纪律

- 结论先行：第一句回答「站不站得住、最弱一环在哪」。
- 五环是检查清单，不是章节模板：逐环平铺输出 = 背模板；围绕最弱一环组织。
- 每个判断标证据等级；没证据的写 🔶 假设，不写成事实。
- Barnum 自检：把产品名换成别家产品重读一遍，判断仍然成立的段落删掉重写。
- 结尾自评三行：最弱的一环 / 最该验证的假设 / 建议的下一步最小动作。

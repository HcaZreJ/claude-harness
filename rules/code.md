# 写代码时的规则

## 测试义务

按**改动内容**定，同时命中多条时取最严的一条：

| 改动内容 | 测试义务 |
|---|---|
| 计费 / 权限 / 判分 / 迁移 / 不可逆数据操作 | 必测，test-first |
| 含条件分支、计算、状态推导 | test-first，≤ 8 例 |
| 普通函数 / 接线 | test-first，≤ 4 例 |
| 纯样式、静态文案 | 跑起来验收，留命令输出或截图 |
| 配置 / 文档 | 无测试义务 |

带业务分支的前端组件按「含条件分支」处理。新增测试目录时跑 `~/.claude/scripts/check-ci-reachability.sh <repo>`，再对照 CI 配置人工核对它的报告：这个脚本会把没有任何 job 跑的目录也报成可达，在 macOS 自带的 grep 下还会截断抽出的命令。确认目录挂进了选中它的 job，CI 选不中的测试从不运行。

## 代码写法

写函数、改函数、review 代码写法时按这六条判定：

1. **主路径留在最外层。** 前置条件用 guard 挡在前面，一条不满足立刻返回；条件超过两三条就收进一个命名的判定函数。
2. **名字给出业务含义。** 变量名答「这是什么」，函数名答「接下来发生什么」。
3. **外部系统的字段名止于适配层。** 应用内部只用自己的领域名字，第三方改字段只改一处。
4. **类型只描述真实存在的状态。** 把「这里一定有值」写进类型，省掉每处用前再判一次。
5. **决策算成值，副作用另起一段。** 业务规则是纯函数，不碰数据库、网络、文件——权限、计费、判分、校验因此才测得动。
6. **错误同时给 code 与 message。** code 给系统判分支，message 给人读；日志带 request id 与 endpoint，凭据不进日志。

判断标准：让下一次改动更容易。

## 文档更新

改动触及下表的事，就地改写对应文档里的那条事实。仓库的 AGENTS.md 写了自己的文档契约时，以仓库的为准。

| 这次改动触及 | 就更新 |
|---|---|
| 项目目的变化 / 使用场景变化 / 目标用户变化 / 核心功能或使用方式变化 / 技术·设计·交互·产品要求变化 / 对标产品变化 | PROJECT.md |
| 新设计范式 / 数据建模规则 / 代码约定 / 新增扩展点配方 | PATTERNS.md |
| 加换删依赖 / 新框架·外部服务·数据库 / 目录结构调整 / 模块增减或职责变 / 核心 data model 变 / 环境变量增减 | TECHSTACK.md |
| 构建·测试·运行·迁移·部署命令或流程 / CI 闸门 / 分支工作流 | DEVFLOW.md |
| 完成某 work-unit | 从 BACKLOG.md 移走 |
| 长期或未来想做的事 | GitHub issues（`gh issue create`）|

纯实现细节、bugfix、不改上述约定的重构，不更新文档。
